# 0002. Хранилище слоями, без миграций до релиза

Статус: заменено решением 0013
Дата: 2026-11-01

## Контекст

Раньше ключи `localStorage` были разбросаны по коду без системы (`redtf:theme`, `redtf:comments`, `redtf:dtf2022`, `redtf:auth:proxy_url`), токены источников лежали внутри манифестов, а кэш данных API — рядом с настройками. Не было версий формата: добавление поля в сохранённый объект теряло его у тех, кто уже сохранял настройки. Нельзя было сказать, что безопасно экспортировать, а что сбросить.

Пользователей у проекта ещё нет, формат данных меняется часто.

## Решение

1. Всё хранится через `persistedState`, ключ `redtf:<слой>:<имя>`. Слои: `settings`, `theme`, `secrets`, `data`, `cache`.
2. Данные лежат в виде `{ v: версия, d: данные }`. Если версия не совпала, данные отбрасываются. Новые поля объектов подхватывают значение по умолчанию.
3. **Миграций и обратной совместимости нет** и не будет до первого релиза. При несовместимом изменении формата поднимается версия или меняется ключ, а разработчик просто входит заново.
4. Токены (`secrets`) отделены от всего остального.

## Последствия

- Код хранилища маленький и однотипный, в нём нет ветвей для старых форматов.
- Любое обновление в разработке может сбросить сохранённое: это принято.
- После релиза этот пункт придётся пересмотреть: потребуется функция `migrate` в `persistedState` или решение «сбрасывать при несовпадении версии». Версия в формате уже есть, так что добавить это можно без смены схемы.
- Токены лежат в открытом виде (у статичного SPA нет секрета для шифрования), но отделение слоя позволяет не отдавать их при экспорте.
