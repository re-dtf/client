# 0003. Наследование тем (`extends`) вместо сабмодулей

Статус: принято
Дата: 2026-11-01

## Контекст

Нужны форки тем: вариант `dtf2022` с другим оформлением, который автоматически получает исправления основной темы. Рассматривались три пути.

1. **Копия папки темы.** Просто, но форк перестаёт получать исправления: надо переносить вручную.
2. **Git-сабмодули или отдельные репозитории.** Решают задачу «код живёт в другом репозитории». Для статичного SPA они усложняют сборку и CI, а исправления основы всё равно приходится подтягивать вручную (обновлять указатель сабмодуля) и разрешать конфликты.
3. **Наследование внутри репозитория.** Тема указывает `extends`, `ThemeLoader` ищет компонент по цепочке тем.

## Решение

Выбрано наследование:

- в манифесте `extends: '<id основы>'`;
- компоненты, стили и схема настроек разрешаются по цепочке «форк, основа, основа основы»;
- `data-theme` хранит цепочку (`"fork dtf2022"`), стили основы подключаются через `[data-theme~="dtf2022"]`;
- значения настроек у форка свои.

## Последствия

- Исправление в основной теме сразу попадает во все форки, ничего не нужно переносить.
- Форк переопределяет только то, что отличается: обычно пара компонентов и токены CSS.
- Форки зависят от публичной поверхности основы: контракта компонентов (`themes/contract.ts`), токенов CSS и схемы настроек. Менять их нужно осознанно.
- Глубокие внутренности основы (`post/`, `comments/`) не являются API. Импортировать их можно, но форк тогда привязан к ним.
- Темы из внешних репозиториев пока не поддерживаются. Если понадобятся, их можно подключать как npm-пакеты с тем же манифестом, не меняя модель.
