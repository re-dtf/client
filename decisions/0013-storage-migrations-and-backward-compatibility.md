# 0013. Миграции хранилища и обратная совместимость при релизе

Статус: принято
Дата: 2026-11-10

## Контекст

Решение 0002 устанавливало запрет на миграции данных до первого релиза: при несовпадении версии в `persistedState` сохранённые данные отбрасывались, а пользователь/разработчик настраивал клиент или входил заново.

С переходом к релизу этот подход недопустим: пользователи сохраняют настройки тем, палитры, авторизацию DTF, токены источников, локальные чёрные списки и статистику. Сброс данных при обновлении формата ухудшает пользовательский опыт и приводит к потере персональных конфигураций.

## Решение

1. **Обратная совместимость по умолчанию**:
   - Новые поля в объектах настроек автоматически подхватывают значения по умолчанию через механизм объединения с `defaults`. Повышение версии для добавления новых опций не требуется.
   - Удалённые или устаревшие свойства игнорируются, не ломая чтение.

2. **Декларативные миграции при смене формата**:
   - `persistedState` и `readPersisted` принимают опциональную функцию преобразования:
     `migrate?: (savedData: unknown, oldVersion: number) => T`.
   - Если сохранённая версия `v` не совпадает с актуальной версией схемы и передана функция `migrate`, вызывается миграция старых данных.
   - При успешной миграции результат сохраняется в `localStorage` уже с новой версией формата, обеспечивая прозрачный и однократный перенос данных.
   - В случае ошибки миграции или отсутствия функции преобразования безопасным фоллбэком остаётся значение по умолчанию.

3. **Слои хранилища сохраняются**:
   - Структура слоёв `settings`, `theme`, `secrets`, `data`, `cache` доказала свою надёжность и сохраняется в полном объёме.

## Последствия

- Обновления клиента больше не приводят к потере пользовательских данных и повторным запросам входа.
- Разработчики могут безопасно изменять структуры сохранённых объектов, описывая функцию миграции для конкретного ключа.
- Синхронный ранний запуск (`bootstrap.ts`) и основное приложение сохраняют общую функцию чтения `readPersisted`.
