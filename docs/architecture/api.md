# Слой API

UI получает данные только через объект `api` (`src/lib/api/index.svelte.ts`) — фасад. Компоненты вызывают `api.getPosts()`, `api.getComments()` и не знают, откуда пришли данные.

```
UI ──► api (фасад) ──┬──► providers/dtf          официальный API DTF
                     └──► providers/source       один на каждый подключённый источник
                              └─ sources/source-fetcher  запрос к эндпоинту из манифеста
```

## Модель данных

`src/lib/api/types.ts` — наши типы: `Post`, `Comment`, `User`, `Profile`, `Session`, `CurrentUser`, `PaginatedResult<T>` и так далее. У каждого поста и комментария есть `sourceId`: `'dtf'` или id подключённого источника. Это композитный ключ для `{#each}` (`sourceId + '_' + id`) и для маршрутизации обратных действий (реакция уходит в тот источник, откуда пришёл комментарий).

Сырые ответы чужих API в типы не попадают: провайдер переводит их в наши типы сам (`providers/dtf/mappers.ts`).

## Провайдер

Интерфейс `ApiProvider`: обязательное есть у всех (`getPosts`, `getPost`, `getComments`), остальное по возможностям провайдера, методы необязательные. Если метода нет, провайдер этого не умеет, и проверять это нужно через `provider.method?`, а не ловить исключение «не реализовано».

| Провайдер | Умеет |
| --- | --- |
| `providers/dtf` | всё: чтение, вход, профили, редактор, реакции на посты и комментарии, закладки, подписки, комментарии (запись и правка), уведомления, права на комментарии, история поста |
| `providers/source.ts` | чтение (посты, пост, комментарии), `getReplacedComments`, `getRestoredComments`, `reactToComment` — если эндпоинт есть в манифесте |

### Провайдер DTF (`providers/dtf/`)

| Файл | Что внутри |
| --- | --- |
| `client.ts` | адреса и версии API, `fetchWithAuth` (токен, повтор после обновления при 401), `refreshSession`, `requireAuth`, адрес прокси |
| `auth.ts` | вход по паролю (только через прокси) и по токену |
| `mappers.ts` | перевод ответов DTF в наши типы |
| `index.ts` | `dtfApiProvider`: методы API |

Токены: заголовок `JWTAuthorization: Bearer …` (старый `x-authenticate` не использовать). Вход и обновление токена уходят через CORS-прокси из настроек, остальные запросы — напрямую на `api.dtf.ru`. Описание самого API DTF: подмодуль `.agents/skills/dtf-api` ([re-dtf/api-docs](https://github.com/re-dtf/api-docs), [сайт](https://re-dtf.github.io/api-docs/)).

### Провайдер источника (`providers/source.ts`)

`createSourceProvider(source)` собирает провайдер из манифеста: каждый метод вызывает `fetchFromSource` для нужного эндпоинта. Он же проверяет, что ответ — список (`items` — массив), иначе кидает понятную ошибку: источник чужой, и верить его ответу нельзя. Разрешения здесь не проверяются, это делает фасад. Подробнее про манифесты и разрешения: [data-sources](data-sources/README.md).

## Фасад

Фасад делает то, что не принадлежит одному провайдеру:

- **Слияние.** `getPosts` опрашивает DTF и все включённые источники с эндпоинтом `getPosts` параллельно и сливает посты (`sources/merger.ts`). Курсоры пагинации у каждого источника свои, они лежат в `cursors` результата.
- **Комментарии.** `getComments` берёт основные комментарии у источника поста и добавляет или подменяет их комментариями других источников, если им выдано разрешение `mutate:comments:append` или `mutate:comments:replace` для этого источника. При наличии разрешения `mutate:comments:restore` фасад неразрушающе накладывает текст и медиа из архива на удалённые заглушки DTF (`comment.restored`) с проверкой автора. Опрос восстанавливающих источников ленивый: если на странице нет удалённых комментариев, подходящих под настройки пользователя, запрос к архиву не выполняется. Непагинированные источники (`paged: false`) кэшируются в памяти на время работы с постом. У источника один режим: подмена важнее восстановления, восстановление важнее добавления. Основной и дополнительные источники опрашиваются параллельно; восстанавливающие ждут только основную порцию, чтобы понять, нужны ли они.
- **Рейтинг.** Если включена настройка сортировки по реакциям, каждая порция «Популярного» и комментариев «Лучшие» пересортировывается по рейтингу пользователя ([реакции и рейтинг](settings.md#реакции-и-рейтинг)). Страницы сервера не склеиваются заново: порядок меняется только внутри порции.
- **Разрешения.** Перед записью (реакция в стороннем источнике) фасад проверяет `write:reactions`.
- **Выбор провайдера.** `providerFor(sourceId)` отдаёт DTF или провайдер включённого источника, а для неизвестного кидает ошибку.

Остальные методы (профили, редактор, вход, действия вошедшего пользователя: реакции на посты, закладки, подписки, комментарии, уведомления) — прямые вызовы провайдера DTF.

У DTF каждый метод живёт на своей версии (`/v2.4/comment/add`, `/v2.1/favorite`), поэтому новые методы берут адрес через `apiV('2.4')` из `client.ts`, а не заводят константу на каждую версию. Тело записей — multipart (`formOf` в `providers/dtf/index.ts`); часть методов отвечает 200 с `error` в теле, его разбирает `resultOf`.

## Ошибки

- Провайдеры превращают сетевые ошибки, таймауты и плохие ответы в `Error` с понятным текстом. Сырые ошибки `fetch` до UI не доходят.
- Если не ответил **DTF** — ошибка уходит вызывающему, страница показывает её.
- Если не ответил **дополнительный источник** — остальные результаты показываются, а причина пишется в консоль (`[reDTF] Источник 'x' не ответил`). Лента не должна ломаться из-за чужого сервера.
- Запрос к источнику ограничен 3 секундами.

## Вошедший пользователь

`api/currentUser.svelte.ts` хранит данные вошедшего пользователя DTF (для шапки и меню профиля) и кэширует их в `redtf:cache:current-user`, чтобы аватар появлялся сразу, до ответа API. `currentUser.load()` обновляет данные один раз за загрузку страницы, `currentUser.clear()` вызывается при выходе.

`api/notifications.svelte.ts` — уведомления вошедшего пользователя для колокольчика в шапке: `load()`, `unread`, `markAllRead()`. Состояние «прочитано» берётся из `status` уведомления DTF (`1` — новое), это предположение из HAR, живьём оно не проверялось.
